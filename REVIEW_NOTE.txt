TemplateWing 2.9.0: Review Notes
=================================

Minimum Thunderbird: 128.0
License: Mozilla Public License 2.0
Author: Julia Kalder <mail@julia-kalder.de>
Repository: https://github.com/JuliaKalder/TemplateWing

Changes
-------

2.9.0
  New feature: the {RECIPIENT_NICKNAME} template variable. It fills in
  the Nickname field of the address-book contact that matches the first
  To: recipient, so a template can greet someone by the name they
  actually use while the contact card stays formal.

  This is the only change that touches permissions, and it does so
  deliberately as an OPTIONAL one:

    "optional_permissions": ["addressBooks"]

  Nothing is requested at install or update time. The add-on asks for
  addressBooks only when the user presses "Allow address book access"
  in the options page, next to the variable that needs it. Users who
  never use this variable are never asked, and an existing installation
  updates without a permission prompt.

  What the add-on does with the permission: for a template that
  actually contains {RECIPIENT_NICKNAME} (or a conditional on
  recipient.nickname), it runs one contacts.quickSearch() for the
  recipient's email address at insert time, verifies the returned
  contact really carries that address, and reads NICKNAME out of its
  vCard. Nothing is written, nothing is stored, nothing leaves the
  machine. A withheld permission, an unknown contact or a contact
  without a nickname all resolve to the empty string; template
  insertion never fails over it. All of it lives in
  modules/address-book.js.

  New file: modules/address-book.js (listed in scripts/xpi-files.mjs).

  Recipient names: a recipient with no display name used to be
  greeted by the local part of its address ("julia.kalder"). The
  name now comes from the matching address-book contact where the
  permission allows it, and is otherwise derived from the address
  itself ("Julia Kalder" / "Julia"). A display name supplied with
  the recipient is never overwritten. This widens the contact
  lookup described above from {RECIPIENT_NICKNAME} to any
  recipient variable, but only when the address arrived without a
  display name, and still only with the permission granted.

  A cancelled ask-on-insert dialog no longer writes an error to the
  console. It was never shown to the user, but it made a clean run
  look broken to anyone reading the error console.

  Localisation: the rich-text toolbar of the template editor
  (bold/italic/lists/paragraph format/HTML view) and the recipient
  field placeholders were hardcoded English in every locale. They
  now go through i18n like the rest of the UI; 16 keys added to all
  seven locales.

  Behaviour change, no new permission: template recipients are now
  merged into the compose window's To/Cc/Bcc instead of replacing
  them. Assigning them deleted whatever address the user had already
  picked, which also made the order in which the recipient variables
  resolve correctly ("choose recipient, then insert") the order that
  lost data. Existing entries keep their position; duplicates are
  dropped by address.

  Two follow-ups from the same root cause — variables are resolved
  once, when the template is inserted:
    * When a template greets the recipient and neither the window nor
      the template supplies an address, the existing ask-on-insert
      dialog also asks for one. Blank is accepted and keeps the
      fallback wording. The auto-insert path deliberately does not
      ask; a dialog opening by itself on every new compose window
      would be worse than the fallback.
    * The popup offers to run the last inserted template again against
      the recipients the window has now, replacing the body. Tracked
      in memory per compose tab, dropped when the tab closes; nothing
      is stored.

2.8.1
  Bugfix: templates set to "Insert at beginning" did not insert their
  body at all. The body was concatenated in front of the document that
  compose.getComposeDetails() returns, and Thunderbird 128/140 ESR
  rebuild the compose document by reading the head from "<head" and the
  body from "<body" onwards, so anything ahead of those markers was
  discarded. It is now spliced inside the body element. Append, which
  survived by landing at the other end, takes the same route.
  Bugfix: on plain-text accounts no template body was inserted in any
  mode. Thunderbird drops details.body on a plain-text composer and
  expects plainTextBody; the add-on only ever set body. Plain-text
  composers now receive the text as plainTextBody.
  No new permissions, no new files, no API surface added.


Reproducing the XPI
-------------------
Requires Node.js 20+ and the zip command line utility.

  node scripts/build-xpi.mjs

Output: templatewing-2.9.0.xpi (142 KB / 145,420 bytes)
SHA-256: 5c951e06a9040fe01d77bea21dc79b3d4b036e4953095c6858ee724d9cb3e02e

The build is byte reproducible, so this hash can be verified rather
than trusted. Rebuilding from the source archive gives the identical
hash on any machine, in any timezone, under any umask. Compare with:

  sha256sum rebuilt.xpi          (macOS: shasum -a 256 rebuilt.xpi)

To get there, the builder stages the files into a scratch directory,
stamps them 2020-01-01T00:00:00Z and mode 0644, runs zip with -X to
drop the timestamp and uid/gid extra fields, and pins TZ to UTC.
.gitattributes pins line endings to LF so a Windows clone produces the
same bytes. CI performs this check on every push and also fails if this
file quotes a stale hash.
